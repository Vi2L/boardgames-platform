О портале

базовое

Parser Debug Portal — внутренний веб-«cockpit» для работы с каталогом настольных игр и парсерами магазинов. Объединяет три бэкенд-сервиса:

СервисРольURL в dev
parsers парсинг цен 6+ магазинов :8001
catalog каталог игр + ML-матчинг :8002
web-test сам портал (этот UI) :8000

Открытие портала

  • Локально: http://localhost:8000/
  • Dev-режим фронта: http://localhost:5173/ (Vite, hot-reload)

Навигация

Сайдбар слева содержит 11 разделов + бейдж здоровья всех сервисов внизу. Сворачивается/разворачивается кнопкой в правом верхнем углу сайдбара — состояние сохраняется в localStorage.

Health-бейдж Внизу сайдбара виден индикатор состояния parsers и catalog. Клик показывает popover с подробностями: размер БД parsers, total games в каталоге, число unmatched оффер'ов.

Cmd+K — командная палитра

Глобальный hotkey ⌘+K (или Ctrl+K) открывает палитру с быстрыми действиями: переход в разделы, перезапуск последнего поиска с force-refresh, запуск любимых поисков (Favorites).

Cmd+/ — фокус на поиске

Из любого места портала ⌘+/ переключает на главную и ставит фокус в поле запроса. Удобно для быстрой проверки цены.

Поиск /

главный экран

Streaming-поиск (SSE) по 6+ магазинам параллельно. По мере того как каждый парсер отвечает, результаты подмешиваются в таблицу — не нужно ждать медленный магазин.

Форма поиска

  • Поле запроса — название игры. Фокус по ⌘+/.
  • Магазины — мульти-select. Пусто = «все доступные».
  • Лимит — по умолчанию 100 строк, потолок 500.
  • Refresh — мимо кеша (обращается напрямую к магазину).
  • Показать товары не в наличии — иначе скрытые товары (HG availability=false, CrowdGames in_stock=false) убираются из таблицы.

Колонки таблицы результатов

МагазинЦветной бейдж + ссылка на оригинал

Лояльность (личные скидки)

Кнопка Лояльность в шапке открывает панель настройки. Поддерживаются:

  • HobbyGames — до 15% бонусами от цены товара (если товар не на акции extra.on_sale).
  • Лавка игр — фиксированный процент + донор-карта VK.
Оптимистичная цена HG-бонусы применяются «по каждому товару отдельно» (min(пул, 15% × цена)). При покупке нескольких товаров одной корзиной фактическая скидка может быть меньше. Дисклеймер указан в самой LoyaltyPanel.

Бейджи в таблице

  • sale — цена со скидкой (HG extra.on_sale); зачёркнутая extra.original_price рядом.
  • нет в наличии — товар скрыт, если выключен фильтр.
  • loyalty -N₽ — применена скидка из настроек.

Действия над результатом

  • 📷 Snapshot — сохраняет текущий результат в локальную БД портала. Можно потом сравнить с другим прогоном на странице Тесты.
  • ⭐ Сохранить в Избранное — запоминает запрос + магазины + конфиг лояльности. Запускается одним кликом из ⌘+K.
  • 👁 Watch-mode — периодически (по таймеру) повторяет запрос с force-refresh, обновляет цены в реальном времени.
  • ⬇️ CSV / JSON — выгрузка текущей таблицы.

ProductDrawer — карточка товара

Клик по строке открывает drawer с:

  • Полным заголовком, ценой, ссылкой на магазин.
  • Графиком истории цен (по price_observations).
  • Сырыми полями extra (наличие, акции, original_price).
  • Связанной игрой из каталога, если матчинг проставил game_id.

Deep-link и шеринг ссылок

Параметры в URL: ?q=&stores=&limit=&refresh=&auto=1. С auto=1 поиск стартует автоматически — удобно для шеринга и для команды «Запустить» из палитры.

Парсеры /parsers

диагностика

Сетка карточек: одна карточка на парсер. Сверху — бейдж доступности parsers API (обновляется каждые 15 сек).

Карточка парсера

  • Slug + название магазина
  • Версия и описание (берётся из метаданных парсера)
  • Run — запускает парсер с введённым запросом, показывает результаты прямо в карточке. Удобно «пощупать» один источник, не уходя в /search.
  • 🗑 Очистить кеш — инвалидирует кеш этого магазина. Дальше первый запрос пойдёт live.
  • Status — последний пинг, latency, ошибки.
Когда сюда заходить После добавления нового парсера, после деплоя парсера с правками, для точечной проверки «жив или мёртв». Для глубокой диагностики (Live vs cache, raw HTTP, contract) — раздел Debug.

Debug /debug

диагностика

5 вкладок диагностических инструментов. Все — про парсеры.

Live Test

Запускает выбранный парсер по запросу мимо кеша и показывает сырой ParsedProduct — то, что парсер реально вернул из магазина. Используется, чтобы:

  • Проверить, парсится ли новая категория товаров
  • Увидеть все поля, включая extra.*
  • Поймать падение или таймаут до того, как оно попадёт в кеш

Сравнить (cache vs live)

Side-by-side diff: что лежит в кеше vs что отдаст live-парсер по тому же URL. Полезно для расследования «почему цена не обновилась», «почему в поиске старые данные».

По URL (URL probe)

Парсит конкретный URL карточки товара (а не запрос/категорию). Удобно для:

  • Проверки парсинга нового шаблона страницы
  • Воспроизведения бага по конкретной ссылке
  • Отладки regex / селекторов на живом ответе

Контракт

Показывает JSON-schema ParsedProduct + heatmap покрытия полей по магазинам: какие парсеры какие поля заполняют. Тёмные ячейки = поле почти не приходит — повод посмотреть, мёртвый ли это парсер или поле опциональное.

Raw HTTP snapshots

Таблица всех сохранённых HTTP-ответов (headers + body) от магазинов. Клик по строке открывает drawer с raw-ответом — можно скопировать, искать в нём regex'ом, понять почему парсер «не видит» товар.

База данных /database

аналитика

Большая страница с 7 вкладками. Сверху сводный health-блок — 4 кликабельные карточки (товары портала, магазины, журнал, БД parsers), каждая ведёт на соответствующую вкладку.

Товары портала

Локальный кеш товаров, найденных через /search. Можно фильтровать по магазину, сортировать (свежие / цена / алфавит), удалять. Клик по строке открывает ProductDrawer (как на /search).

Магазины

Список парсеров с метриками: success_rate_24h, avg_response_ms, последний успех/ошибка. Сортировка по умолчанию — «проблемные сначала» (низкий success-rate).

Журнал поисков

История запросов через /search: что искали, сколько результатов, сколько мс заняло. Полезно для расследования «откуда пользователь видел такие-то цены».

БД parsers — inventory

По каждому магазину: products_count, observations_count, min/mean/max цена в рублях, дата первого и последнего наблюдения. Per-column сортировка (клик по заголовку).

БД parsers — товары

Низкоуровневый browser таблицы products в parsers БД. Поиск по title, фильтр по магазину, удаление observations (требует подтверждения).

БД parsers — аналитика

  • Latency — p50/p95/p99 по каждому парсеру за последние сутки.
  • Top queries — самые частые запросы + cache_hit_rate (0..100).
  • Тихие сбои — empty-responses (магазин ответил 200, но 0 товаров).

БД parsers — графики

Гистограмма распределения цен по диапазонам. Помогает увидеть «странные» кластера — копейки, миллионы и т.п. (артефакты парсинга).

Каталог /catalog

основной workflow

Главный «склад» канонических игр. 5 вкладок.

Каталог

  • Поиск — fuzzy через pg_trgm (опечатки прощаются). История запросов сохраняется в SuggestInput.
  • Таблица игр — название (RU + EN), BGG ID, rating, год, кол-во алиасов.
  • Клик по строке → GameDetailDrawer: полная карточка с BGG / Wikidata / aliases.
  • Кнопки сверху:
    • Новая игра — открывает GameEditor (ручное создание).
    • Импорт BGG / Tesera — ImportWizard с polling до завершения.
    • Backup — pg_dump каталога в .scratch/backups/ (gitignored).

Drawer карточки игры

  • BggCard — рейтинг, ранги, веса (complexity), картинка.
  • WikidataCard — русское название, описание, год, авторы (если обогащено).
  • AliasList / AliasEditor — CRUD алиасов с verified-флагом. Алиасы повышают score в pg_trgm матчинге.
  • Edit — открывает GameEditor для правки полей.
  • Merge — слить эту игру с другой (MergeDialog). Все offers переезжают на оставшуюся, дубликат удаляется.

Очередь матчинга (legacy)

Список offers без game_id. Для каждого — топ-N кандидатов с pg_trgm score в LinkPicker. Кнопки Связать, Отклонить, Reassess.

Header сверху — статистика очереди (по магазинам и score-buckets). Кнопка Reassess all прогоняет всю очередь повторно (полезно после добавления алиасов).

Новая admin-панель v2 живёт на /matching. Эта вкладка остаётся для оперативной ручной работы с конкретными offers.

Журнал матчинга

Историческая лента match_log: какие offers были связаны/отклонены, каким методом (T0 cache / T1 trgm / T2 ML / manual), кем (auto / оператор). С возможностью revert — откатить решение и вернуть offer в очередь.

Промоушен Dicefest

Workflow: source-снимок Dicefest → staging → canonical. Позволяет «промоутить» подтверждённые игры из временной staging-таблицы в основную games.

BGG (импорт)

Дополнительная панель импорта BGG (помимо ImportWizard).

Матчинг /matching

admin panel

Operator console для ML-матчинга v2. Header сверху — live-индикаторы (ML status + queue counts). 5 вкладок.

Архитектура pipeline (вкратце)

TierЧтоТип
T0Cache hit (нормализованный title → game_id)sync
T1pg_trgm ≥ 0.92 — почти точное совпадениеsync
T2ML embedding similarity (Ollama)async, worker
T3ML re-ranking «сложных»async
T4Manual queue (оператор)UI

Контроль

  • Kill-switch — глобальный выключатель ML-tier'ов. Используется при инциденте Ollama/моделей. T0/T1 продолжают работать.
  • ML-модели — список доступных моделей Ollama, текущая выбранная, кнопка Warmup (прогрев — первый запрос всегда медленный).
  • Worker — статус ML-воркера, queue depth, last error.
  • CircuitStateBadge — closed / open / half-open. Open = ML временно отключён из-за серии ошибок.
Когда выключать ML Ollama залипла / модель отдаёт мусор / процесс жрёт RAM. После kill-switch новые offers пойдут T0→T1→T4 (минуя T2/T3). После рестарта Ollama — Warmup и снять kill-switch.

Очередь

Таблица match_queue: pending / processing / skipped / failed. Фильтры по магазину, score-bucket, статусу. Кнопка Re-enqueue skipped — возвращает в очередь записи, которые ML пропустил (обычно после изменения порогов/моделей).

Журнал

Тот же MatchLogTab, что на /catalog → «Журнал матчинга». Показан здесь для удобства — оператор остаётся внутри admin-панели.

Штучный

Прогон одного offer через весь pipeline с progress-drawer'ом: видно, на каком tier'е offer закрепился и почему другие tier'ы не сработали. Идеально для отладки «почему этот offer не матчится».

Help (встроенная)

Полная документация по матчингу: ASCII-схема pipeline, когда вкл/выкл ML, когда re-enqueue, как читать match_log, troubleshooting, глоссарий. Sticky-навигация слева внутри самой вкладки.

BGG Sync /bgg-sync

периодика

Cockpit для периодической синхронизации с BoardGameGeek. 5 вкладок.

Расписание

Health-блок 3 scheduled-job'ов (rank import, hotness fetch, geeklist refresh) + cron editor — позволяет изменить расписание прямо из UI.

История

Таблица ImportJob'ов (manual / scheduled) с фильтрами. Видны статусы (running / done / failed), сколько игр обработано, длительность.

Hotness

Текущий снимок BGG /hot + история + diff: новые (попавшие в hot) и выбывшие по сравнению с прошлым снимком. Кнопка «Обновить сейчас» — ручной refresh.

GeekList

Импорт кураторских списков (Top 50 Most Played etc.) по ID GeekList'а. Полезно для пополнения каталога играми, которые не лежат в hot/top.

Без BGG ID

Список игр из каталога, у которых нет bgg_id. По каждой — прямая ссылка на поиск в BGG, чтобы вручную найти и привязать.

Источники /sources

provider-agnostic

Управление актуализацией данных из внешних источников (Dicefest сейчас, BGA / Dicebreaker позже).

Слева — ProviderSidebar с провайдерами. Текущий провайдер в URL: /sources/dicefest. Deep-link работает, история back/forward сохраняется.

Detection

Сухой прогон скрапа: показывает что будет — diff между текущим source-снимком и тем, что в БД. Кнопки Apply (применить) и Discard (отбросить).

Staging

Та же PromotionPanel, что на /catalog → Промоушен Dicefest. Промоушен из staging-таблицы (предварительно подтверждённое) в canonical games.

Match params

Настройка параметров матчинга для этого провайдера: threshold, веса по полям, external-id маппинг. Поддерживает сохранённые профили — переключаться без правки кода.

Logs

Журнал промоушенов и scrape runs. Кто, когда, что промоутил.

Тесты (QA) /testing

регресс

3 вкладки.

Snapshots

Сохранённые прогоны /search. Выберите два (max) и нажмите Сравнить — откроется DiffView с категориями изменений:

  • price — цена сменилась
  • lost — товар пропал из выдачи
  • gained — новый товар
  • raw — изменились сырые поля
  • field — изменилось какое-то extra.* поле

Сьюты

Test-сьют = набор запросов с ожиданиями (baselines). Запускается один раз — runner прогоняет все запросы и сверяет результаты с baseline (например, min_count ≥ 10). Зелёное / красное по каждому запросу. Используется для регрессионных проверок после правок парсеров.

Избранное (Favorites)

Сохранённые поисковые запросы с preset (всё UI-состояние: магазины, лимит, show_out_of_stock, конфиг лояльности). Один клик из ⌘+K → восстанавливаем точное состояние.

DLQ /dlq

аварийный

Dead-Letter Queue для отправки оффер'ов из parsers в catalog через POST /ingest/offers. Если catalog был недоступен или ответил 5xx, parsers не теряет данные — складывает payload в SQLite-таблицу catalog_dlq.

Действия

  • Replay (по одной записи) — переотправляет payload. Успех → запись удаляется.
  • Replay all (batch 50) — заявляет всё подряд. Показывает ✓ N успешно, ✗ M провалено.
  • Delete — удаляет запись без повторной отправки (если payload корявый).
Когда сюда смотреть После downtime catalog'а. Если на странице висит «N зависших батчей» — нажать Replay all. Если payload broken (старый формат) — посмотреть конкретный JSON и решить: replay или delete.

Список обновляется автоматически каждые 30 сек. Подтверждение требуется на destructive операции (delete, replay-all).

Статус /status

мониторинг

История пингов обоих сервисов для ретроспектив. При входе на страницу — автопинг, далее каждые 30 сек записывается точка в ping_history.

Что видно

  • График unmatched_offers во времени — основная метрика прогресса матчинга.
  • График total_games на вторичной оси — рост каталога.
  • Timeline-лента статусов parsers / catalog (зелёный/красный).
  • Текущий статус (последний пинг).

Окна

Селектор периода: 1ч / 6ч / 24ч / 7д.

Рецепты — типовые workflow

шпаргалка
🔎 Проверить цену игры быстро
  1. На любой странице → ⌘+/ (попадаешь на /).
  2. Ввести название, нажать Найти.
  3. В таблице видишь цены с Min 30д и Δ. Клик по строке → ProductDrawer с историей.
🆕 Добавить новую игру в каталог
  1. /catalog → Импорт BGG / Tesera (ImportWizard).
  2. Ввести BGG ID или название, дождаться job (polling).
  3. Или вручную: Новая игра → GameEditor.
  4. Если есть оффер'ы без матча — /catalog → Очередь матчинга → Reassess all.
🔗 Связать offer вручную
  1. /catalog → Очередь матчинга.
  2. Найти offer в списке. Слева видны топ-N кандидатов с pg_trgm score.
  3. Если правильная игра среди кандидатов — Связать.
  4. Если нет — Отклонить (offer уйдёт в фильтр «не игра»).
  5. Альтернативно — добавить алиас к нужной игре в /catalog и нажать Reassess на этом offer.
🩺 Понять, почему парсер не работает
  1. /parsers — посмотреть, доступен ли. Если красный — проблема в API parsers.
  2. /debug → Live Test — запустить парсер мимо кеша по тестовому запросу.
  3. /debug → Сравнить — увидеть, отличается ли live от cache.
  4. /debug → Raw HTTP — посмотреть, что магазин реально отдаёт.
  5. /database → parsers: аналитика — latency, error rate, empty-responses.
⚙️ ML-матчер «залип» / отдаёт мусор
  1. /matching → Контроль.
  2. Нажать Kill-switch — выключить ML-tier'ы. T0/T1 продолжают работать.
  3. Перезапустить Ollama / проверить модели.
  4. Нажать Warmup, дождаться готовности.
  5. Снять kill-switch.
  6. /matching → Очередь → Re-enqueue skipped — вернуть в обработку то, что ML пропустил.
📨 После downtime catalog
  1. /dlq — если висят зависшие батчи, нажать Replay all.
  2. Проверить, что число падает к нулю.
  3. Если payload сломан (старый формат) — посмотреть конкретный JSON и решить delete vs replay.
🧪 Регрессия после правок парсера
  1. До правок: /search прогон → Сохранить snapshot.
  2. Деплой парсера.
  3. После: повторить /search с force-refresh → второй snapshot.
  4. /testing → выбрать оба → Сравнить. Видно: цены поменялись, товары потерялись/появились.
📊 Backup каталога перед опасной операцией
  1. /catalog → кнопка Backup в шапке.
  2. pg_dump попадает в .scratch/backups/ (gitignored, ротация — 10 свежих).
  3. Restore: bin/backup-catalog.sh restore <file>.

Troubleshooting

когда сломалось

Health-бейдж в сайдбаре красный

Один из соседей (parsers / catalog) недоступен. Проверить:

  • docker compose ps — все 4 контейнера healthy.
  • docker logs bg-parsers / bg-catalog — что в логах.
  • Health-popover в сайдбаре — какая именно метрика красная.

Чёрный экран на /database

Исторически было: фронт обращался к несуществующим полям ответа parsers. Если воспроизводится снова — проверить DevTools console и сравнить с реальным ответом GET /api/parsers-db/*.

«Cache hit» при force-refresh

Force-refresh идёт мимо кеша parsers, но не мимо кеша браузера. Hard reload (⌘+⇧+R) или Очистить кеш в /parsers.

Поиск отдаёт 0 результатов

  • Выключен ли фильтр Показать товары не в наличии?
  • Все ли магазины выбраны?
  • /parsers — все ли парсеры зелёные?
  • /debug → Live Test по одному магазину — отвечает ли он вообще.

Замёрзший offer в очереди матчинга

Если оффер «застрял» в pending много часов:

  • /matching → Контроль — жив ли worker, нет ли open circuit breaker.
  • /matching → Очередь → Re-enqueue skipped.
  • /matching → Штучный — прогнать конкретный offer и посмотреть, на каком tier'е затыкается.

DLQ растёт

Если /dlq показывает много зависших батчей и число растёт — значит catalog не принимает ingest. Скорее всего поломка контракта (POST /ingest/offers). Проверить: docker logs bg-catalog | grep ingest.

Импорт BGG висит «running»

ImportWizard polling'ит job. Если статус не меняется > 5 мин — посмотреть логи catalog. Иногда BGG отдаёт 202 (rate-limit) — ждать. Polling auto-stop'ится по статусу done/failed.
